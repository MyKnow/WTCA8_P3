# 로또 프로젝트

## 구현 흐름

1. **로또 구입 금액 입력 (1000원 단위)**
    - 검증 사항
        - 빈 문자열이 아닌지
        - 숫자로 변환 가능한지
        - 양수인지
        - 1000 단위인지
2. **발행 로또 수량 및 번호 출력**
    - 발행한 로또 수량 출력
    - 각 로또 번호 생성 후 오름차순 정렬 및 출력
3. **당첨 번호 6개 입력**
    - 검증 사항
        - 빈 문자열이 아닌지
        - `,`로 나눈 결과가 6개인지
        - 숫자로 변환 가능한지
        - 1~45 사이의 숫자인지
        - 중복 숫자가 없는지
4. **보너스 번호 1개 입력**
    - 검증 사항
        - 빈 문자열이 아닌지
        - 숫자로 변환 가능한지
        - 1~45 사이의 숫자인지
        - 당첨 번호와 중복되지 않는지
5. **당첨 내역 출력**
    - 각 구매 로또 번호와 당첨 번호 비교
        - 일치하는 숫자 수 확인
        - 보너스 번호 일치 여부 확인
        - 등수 결정
            1. 6개 일치: 1등
            2. 5개 + 보너스 1개 일치: 2등
            3. 5개 일치: 3등
            4. 4개 일치: 4등
            5. 3개 일치: 5등
    - 등수별 통계 출력
6. **총 수익률 출력**

## 프로젝트 후기

이번 프로젝트에서 LottoController 구조를 점진적으로 개선하며 SRP와 테스트 용이성을 동시에 고려하는 방법을 실험했다. 초기에는 `run()`에서 입력, 로직, 출력이 모두 섞여 있어 테스트가 어렵고
결과 불일치 가능성이 있었지만, `handlePurchase()`, `handleRankResult()`, `handleRateOfReturn()` 같은 단계별 메서드로 분리하고 `lazy` 속성을 활용해
lottery와 결과를 재사용하도록 리팩터링함으로써 문제를 해결했다. 또한 main()에서는 단순히 `run()`을 호출하고 출력은 Controller 내부에서 처리하도록 변경하여 가독성과 책임 분리를 개선했고,
OutputView 출력 캡처를 활용한 단위 테스트도 가능해졌다. 이 과정을 통해 코틀린에서 lazy 초기화, vararg 활용, 입력/출력 분리 등 실무적인 설계와 테스트 전략을 함께 적용하는 경험을 얻었다.

## 배운 점

- Controller, Model, View 패키지를 중심으로 설계와 테스트 전략을 이해했다.
    - `handlePurchase()`, `handleRankResult()`, `handleRateOfReturn()`를 단계별로 분리하고 lazy 초기화를 활용해 lottery와 결과를 한 번만 계산하도록
      설계함으로써 run() 호출 시 출력 결과 일관성을 유지할 수 있었다.
- Model 패키지에서 UserWallet, DHLottery, UserWalletCalculator를 통해 도메인 로직을 캡슐화하고 Validator를 적용함으로써 입력값 안전성을 확보하였다. 수익률 계산 역시
  모델 내부에서 처리하여 View와 로직을 명확히 분리했다.
- View, Constant, Util 패키지를 활용해 메시지 관리와 재사용 가능한 유틸리티 구현 경험을 얻었다. 메시지 포맷과 상수를 enum/object로 관리하고, NumberFormatter 같은 공통 유틸
  기능을 분리함으로써 SRP를 지키고 테스트 용이성을 확보할 수 있었다.
